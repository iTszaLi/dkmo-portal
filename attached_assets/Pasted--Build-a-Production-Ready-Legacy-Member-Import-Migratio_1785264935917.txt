# Build a Production-Ready Legacy Member Import & Migration System for the DKMO Portal

I have uploaded a legacy member database (TXT/CSV format) that contains thousands of DKMO members collected over many years. This data is inconsistent, contains missing values, duplicate information, different date formats, inconsistent capitalization, and several legacy-specific fields.

**Do NOT build a simple CSV importer.** Build a complete **Legacy Data Migration System** that intelligently understands the old database structure and safely imports it into the new DKMO Portal.

---

# Objective

Create a secure, professional, reusable import system that can migrate thousands of legacy members into the new DKMO Portal database while preserving old information and cleaning the data automatically.

The importer must be production-ready, scalable, fault-tolerant, and suitable for future imports as well.

---

# Legacy Field Mapping

Interpret the legacy columns exactly as follows.

## Id No

This is NOT the new Member ID.

This is only the old member number.

Store it as:

Legacy Member ID

Generate a completely new Member ID for every imported member.

Example:

DKMO-000001

DKMO-000002

DKMO-000003

Never reuse the old ID as the primary key.

---

## Application No

Store as:

Application Number

If blank

Store NULL.

---

## Old Application No

Store separately as:

Old Application Number

Never overwrite the current application number.

---

## First Name

Store as First Name.

---

## Last Name

Store as Last Name.

Many records have blank last names.

This is expected.

---

## Full Name

If Last Name exists

Full Name = First Name + Last Name

If Last Name is blank

Full Name = First Name

Do not leave Full Name empty.

---

## Mobile No

This is the member's Saudi mobile number.

Normalize every number.

Example:

568799520

↓

0568799520

Accept formats like:

05XXXXXXXX

+9665XXXXXXXX

9665XXXXXXXX

Validate every number.

Highlight invalid numbers.

---

## WhatsApp No

If WhatsApp is blank

Automatically copy the Mobile Number.

Otherwise

Store the provided WhatsApp number.

---

## Jamaath

Normalize spelling.

Examples:

surthkal

SURTHKAL

Surthkal

should all become:

Surthkal

If the Jamaath does not exist

Create it automatically.

Do not create duplicates caused by different spelling or capitalization.

---

## Iqama No

Store as Iqama Number.

If blank

Store NULL.

---

## Place Home

Map to:

Native Place

---

## Place Local

Map to:

Current Location

Examples:

Batha

Olaya

Malaz

Shifa

etc.

---

## Date of Birth

Legacy dates are inconsistent.

Examples:

17-Sep-81

11-Feb-70

30-Nov-90

17/09/1981

1981-09-17

Convert every date into:

YYYY-MM-DD

---

# IMPORTANT — Group Column

The "Group" column is NOT a group.

It actually contains the member's Sponsor / Reference Member information.

Example:

07101-Abdul Azeez Bajpe, 503271851

This should be automatically split into:

Reference Member Code

07101

Reference Member Name

Abdul Azeez Bajpe

Reference Mobile

503271851

Store these as separate fields.

If the value is:

DKMO_Regroup

This means:

No Sponsor Assigned

Store Reference Member as NULL.

If the value is blank

Store NULL.

Never import this field as an actual group.

---

## Passport No

Store as Passport Number.

Blank values are allowed.

---

## Mobile Home

This is usually an Indian contact number.

Store separately as:

Home Contact Number

Never overwrite the Saudi mobile number.

---

## NameAll

Ignore this field completely.

It is only a search string created by the old software.

Do NOT import it into the new database.
